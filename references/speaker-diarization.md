# 说话人分离（Diarization）— 选型、实测数据与硬约束

> 全部数据来自 2026-09-28 在本机的实测（Git Bash + 系统 Python 3.9 + ffmpeg 8.1.1）。
> 测试音频：三份真实长录音（结构访谈；20min、2.37h、2.93h 各一）。
> 主脚本：`scripts/transcribe_diarize.py`；配套校验：`references/verify_diarized.py`。

## 1. 选型结论

| 项 | 值 |
|---|---|
| 模型 | `XingChenAGI/XingChenASR-Diarize-V3.0` |
| 端点 | `https://api.siliconflow.cn/v1/audio/transcriptions`（与 OpenAI transcriptions 同形） |
| 请求 | `model` + `language=zh` + `file`（wav/mp3 均可），Bearer 鉴权 |
| 返回 | `{duration, text, segments[], usage}`；`segments[i] = {start, end, text, speaker}` |
| 时间戳 | **秒级浮点，相对本请求所传音频起点** |
| 说话人 | 匿名序号字符串 "1"/"2"…，自动聚类、**不设人数上限** |
| 计费 | 官方价格页（`https://siliconflow.cn/pricing` →「语音模型」表）标注**免费**；`usage.type=duration` 只是计量口径 |

**参数无效**：`speaker_count`、`response_format=verbose_json`、`prompt` 等一律被忽略，返回结构固定（默认就带
`segments`，不需要 `verbose_json`）。**不要写这些参数**，会给人「可以约束人数」的错觉。

**替代品同表**（同样免费，本轮未实测）：`XingChenASR-V3.2`、`XingChenASR-V3.2-Ultra`、
`XingChenGSR-V1.0`、`Qwen/Qwen3-ASR-1.7B`、`FunAudioLLM/SenseVoiceSmall`。付费的只有 TTS：
`fnlp/MOSS-TTSD-v0.5`、`FunAudioLLM/CosyVoice2-0.5B`，均 ¥0.05/千字符。

### ⚠️ 为什么必须换掉 TeleSpeechASR

`TeleAI/TeleSpeechASR`（本 skill 2026-09 之前用的模型）**已从 `/v1/models` 列表中消失**
（2026-09-28 拉取 98 个模型，无任何 `TeleAI/*`），但接口仍能正常调用（实测 600s → 200）。
即 skill 依赖的是一个**已下架、只在后台还活着**的模型，随时可能静默失效。
换到 Diarize 不只是「加功能」，更是**止损**。

## 2. 吞吐（同一台机器、同一 API key）

| 音频时长 | Diarize 耗时 | 同段 TeleSpeechASR |
|---|---|---|
| 600s | **17.2s** | 41.6s |
| 3600s | ~100s | — |
| 7200s | **168s** | — |
| 8500s | **249s** | — |
| 1249s（真实 0926，单片） | **29s** | — |
| 10534s = 2.93h（真实 0918，切 2 片并行） | **250s**（两片各 247s / 249s，并行） | ❌ 整片直接 500 |
| 10534s 切 7 片（对照实验） | 368s（7 片，3 并发分 3 轮） | — |

≈ **28–35× 实时**。换算：2.4 小时录音约 4 分钟出稿。
上传体积：**mp3 32kbps 单声道即可**（1h → 14.4MB，净字数 14149 vs 16k WAV 的 13895，基本等价），
比 WAV 小 8 倍、上传更快，识别质量无可见损失。

## 3. ★单次请求硬上限：**9000 秒（2.5 小时）**，且**与体积无关**

| 输入 | 体积 | 结果 |
|---|---|---|
| 3600s | WAV **115MB** | ✅ 200 |
| 3600s | mp3 32k，14MB | ✅ 200 |
| 7200s | mp3 32k，29MB | ✅ 200（9 个说话人） |
| 7200s | mp3 64k，**68MB** | ✅ 200 |
| 8534s（2.37h） | mp3 32k，34MB | ✅ 200 |
| 8700s / 8900s | 35MB | ✅ 200 |
| **9000s（2.5h）** | 36MB | ❌ **500，连试 4 次全败** |
| 10534s（2.93h） | 42MB | ❌ **500，连试 4 次全败** |

→ **工程安全值取 8500s（≈2h21m）**。`plan_split()` 的切片数是
`ceil(duration / (safe_limit − overlap))`，保证「等分长 + overlap ≤ safe_limit」。

**500 必须重试**：另实测 5194s 的片首次 500、**原样重试即 200**。
脚本内 5 次退避重试（5/10/15/20s）是覆盖这个偶发故障的，不是过度防御。

## 4. ★同一请求内编号全局一致 —— 这是取消切割的核心理由

- 1h 整片：4 个 cluster，`spk1` 全程在问「叫叫什么名？」「你入团了吗？」→ 书记；
  其余 3 个分别是 0–20 / 20–40 / 40–60 分钟出现的申请人。**模型做了全局聚类**。
- 8534s 整片：9–10 个 cluster，`spk1` 段数最多（199 段）＝谈话人。
- **跨请求编号必然漂移**：同一录音切 0–600s / 600–1200s 两片，片一 `spk2`＝申请人、
  片二 `spk1`＝申请人。**固定时长切片正是在制造这个问题**——这也解释并规避了 2026-09-21
  那次「按切片序号硬套名单导致整段错位」的事故根因。

## 5. 跨片对齐（仅超限时用到）：能做，但**不保证完整**

`align_req` 的做法：相邻两片在重叠窗口内，各自把某说话人的话拼接归一化，
用**最长公共子串长度 ≥ `MIN_LCS`（默认 25 字）**判定「同一人」，通过就沿用前片编号，
否则分配新编号并**明确标注「跨片未锚定」**（绝不静默合并）。

### 5.1 好情形：0926 强制切 5 片（每片 370s、重叠 120s）

| 片 | 本地编号 → 全局 | 重叠区 LCS |
|---|---|---|
| 片2 | 1 → G2 / 2 → G1 | 46 字 / 65 字 |
| 片3 | 1 → G2 / 2 → G1 | 48 字 / 47 字 |
| 片4 | 1 → G2 / 2 → G1 | 35 字 / 27 字 |
| 片5 | 1 → G2 / 2 → G1 | 43 字 / 47 字 |
| 片5 | 3 → **新编号（未锚定）** | — |

**8/9 命中，最终编号归属与「整片直传」结果完全一致**（说话人1＝提问方、说话人2＝作答方）。
未命中的那个是 4 秒 3 段的噪声 cluster，被噪声合并规则并入正确的人。

### 5.2 坏情形：0918（2.93h，1 位谈话人 + 6 位申请人依次）

| 切法 | 各片簇数 | 合并后全局编号 | 未锚定 | 备注 |
|---|---|---|---|---|
| **等分 2 片**（5567s / 5267s） | 6 / 9 | **13** | **7（54%）** | 相对更好 |
| 等分 7 片（各 ~1505s） | 3,3,3,4,4,4,5 | **15** | **13（87%）** | 更差 |

**反直觉结论：片切小，局部聚类更准（每片 3–4 人，符合实际），全局结果却更糟。**
原因：①锚定链变长，断链机会变多；②重叠区里能对上的永远只有「当时正在说话的那 2 个」，
多切一刀就多出一处对不上的编号。
→ **衡量质量要看「全局编号数 + 未锚定比例」，不要看「每片几个人」。片数取最小值。**

### 5.3 对齐是**链式**的，断链不会自愈（最重要的一条）

对照两份运行结果最能说明问题（同一条 0918 录音）：

| | 谈话人（书记）的编号命运 |
|---|---|
| 切 2 片 | **合并为 1 个号**：`说话人2` 从 00:00:03 一路到 02:49:42（首末横跨全程） |
| 切 7 片 | **被劈成 2 个号**：`说话人2`（00:00:03–00:49:20）+ `说话人5`（00:52:24–02:55:34） |

7 片那次的断链经过：谈话人在片1/片2 是 G2；**片3 的重叠窗口里他没说够 25 字** → 片3 给他发了
**新编号 G5**；G5 随后在片4–7 一路正确延续。于是同一个人成了 G2 + G5 两个号。

- 一旦某处边界匹配失败，该编号就**永远拿不到更早的身份**——即使它其实就是同一个人。
- 脚本无法自动修（全量文本 LCS 会因口头语重复而误判，例如「你叫什么名字」每场都说；
  非重叠片之间本来就没有相同语句可比）。
  **只能人工按《说话人对照表》的「各片编号分布」归并，再用 `--alias` 固化。**

### 5.4 实用对策

1. **片数取最少**（3h → 2 片）。
2. 必须切时用 `--cuts` 把切点钉在**场次边界**（一次谈话结束、下一位还没开口的 20–60 秒间隙），
   这样谈话人的编号链不会在对话最密集处断开，且重叠区里他一定在说话（他在串场）。
3. **落名主线永远是《说话人对照表》**，不是编号本身。表里已列出每片每个编号的时段与样例句，
   以及「未锚定编号首次出现在哪一片」——这就是人工归并的全部依据。

## 6. 已知缺陷（模型侧，脚本只能缓解）

1. **同一人可能被拆成两个 cluster**（8534s 那份里 `spk1` 与 `spk7` 都在说「核对一下你满 18 周岁」）。
   脚本只自动合并「又短又碎」的**噪声 cluster**（总时长 <120s 且平均单段 <3s 且平均单段 <5 字），
   不自动合并两个正常 cluster——那会误合真的两个人。**判不准就别合**，留给人。
2. **短促插话／重叠话音会生成噪声 cluster**（出现过只有 65 秒、32 段全是「在」「上」的 `spk9`；
   0918 里出现 30s/6 段的 `说话人9`）。脚本对「总时长 <120s 或段数 ≤8」的簇**加 ⚠️碎片标记**，
   但不自动合并——课堂上学生的提问也可能短，自动合会把提问并进老师。
3. **编号只代表聚类，不代表身份**。谁是谁必须按内容判定，成稿必须附《说话人对照表》＋判断依据。
4. **模型自身时间戳偶有倒挂**：实测同一请求内出现 0.04s 级的 `end > next.start`
   （0918 两片那次 77 处）。脚本做单调化收口（完全被覆盖的段文本并入上一段，跨界段裁齐起点），**不丢字**。
5. 模型不吃 `speaker_count`，人多时可能把一个真实的人合并进另一个人（欠分割），
   也可能把一个人拆成两号（过分割）。**没有 API 参数能修，只能人工核**。
6. **段内说话时长不均**：0918 里有的编号 181 段/1108s，有的 6 段/30s；段数多不等于话多，
   也不等于重要。判断身份要看**内容**（问句 vs 答句），不要看段数排序。

## 7. 明确不做：本地 diarization

- 本机 `C:\...\Python39` 里**无** funasr / modelscope / torchaudio / soundfile / librosa / onnxruntime；
  torch 是 **2.8.0+cpu（无 CUDA）**。要上 pyannote / 3D-Speaker / FunASR cam++ 需另装依赖且只能跑 CPU，
  比云端慢一个数量级以上。
- 另：HuggingFace 在本机**不可达**（000），ModelScope 可达——真要本地化只能走 ModelScope。
- **结论：不做。** 云端免费、快 30 倍、已够用；本地方案的唯一优势是「不外传」，属另一条路线，
  面向隐私敏感场景再单独评估，**不作为本 skill 的可选升级项**。

## 8. 隐私与计费

- **免费 ≠ 无成本**。真实代价是 ① 时间（≈4 分钟/2.4h）；② **录音外传**——音频要上传到
  `api.siliconflow.cn`。涉及人事谈话、未公开会议时，**必须先向用户说明并取得同意**。
- **计费无法从 API 自证**：`/v1/user/info` 已废弃（返回 code 20092）；
  `billing/credit`、`account/balance`、`/v1/balance`、`user/balance` 等路径全部 Not Found。
  「免费」的依据是官方价格页；要 100% 确认未扣费，只能到控制台「费用中心」看消耗记录。
  **不要向用户承诺「绝对不扣费」**，说「官方价格页标免费」即可。
